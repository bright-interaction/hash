## Findings (ranked)

### HIGH

#### H1. Telemetry engagement rollup double-counts, unbounded hourly inflation and eventual INT overflow
- file:line: `cmd/worker/telemetry_rollup.go:31-78`, `internal/db/queries/telemetry.sql:21-47`, `internal/db/migrations/00011_telemetry.sql:7-9,42`
- What is wrong: the hourly rollup feeds `AggregateBlockViews` (an all-time SUM over every non-pruned `block.viewed` row for a document, with no `created_at` bound) into `UpsertEngagementSummary`, whose `ON CONFLICT` is additive (`total_views = document_engagement_summary.total_views + EXCLUDED.total_views`, not `= EXCLUDED`). `ListDocumentsWithRecentTelemetry` re-selects any document with telemetry in the last 25h every tick, so the entire running total is re-added each hour. The migration comment at `00011_telemetry.sql:7-9` says the worker "deletes the raw rows" after rollup, which would have made the additive upsert correct, but that per-rollup delete was never implemented (the only delete is the 90-day `PruneTelemetryOlderThan`).
- Concrete scenario: a document that keeps receiving `block.viewed` events across ticks. After 8 hourly ticks a true 40 views is reported as 180 (roughly 4x and diverging). `total_views` is `INT`, so a sufficiently active block eventually hits Postgres "integer out of range" and the per-block upsert errors permanently, killing that document's engagement rollup.
- Fix: pick ONE. Either add a `created_at > $window` bound to `AggregateBlockViews` matching a non-overlapping tick and keep the additive upsert, or keep the full-history aggregate and change the upsert to replace (`total_views = EXCLUDED.total_views`). Do not do both. If the additive+delete design is intended, implement the post-rollup raw-row delete the migration comment already promises.
- Verification: CONFIRMED. Single-caller path, unwindowed SUM, additive ON CONFLICT, no post-rollup delete, INT column, all quoted at file:line by the verifier.

#### H2. Terminal audit-chain event committed in a separate transaction, silently dropped on a transient failure, no backfill
- file:line: `internal/sign/flow.go:329-346` (Sign), `:433-474` (Accept and CompleteAcknowledgedDocument), `:490` (afterFinalize), `:692` (Decline); root cause `internal/audit/log.go:154-216`; reaper gap `internal/db/queries/documents.sql:173-188` (`GetStrandedDocuments`).
- Base severity is MEDIUM; it escalates to HIGH for acknowledgement-mode documents. Ranked here on the escalation because it re-opens the 2026-07-17 HIGH-3 tamper-evidence hole through a non-attacker path.
- What is wrong: every state transition commits its own transaction first, then emits the legal audit event via `e.Audit.Log(...)` post-commit with the returned error discarded (`_, _ =`). `audit.Log` opens its own transaction and returns non-nil on any transient condition (pool.Begin, chain lock, the fail-closed head read, insert, or commit). Because the error is discarded, a transient blip drops the chain event while the state change is already durable. No worker backfills it: `GetStrandedDocuments` keys on `status = 'in_progress' AND final_pdf_key IS NULL`, so an already-completed document is never revisited.
- Concrete scenario: an acknowledgement-mode document (no ed25519 cert, so the hash chain is the only tamper-evidence layer). The acceptor accepts under load, the document reaches `completed` with `final_pdf_key`/`final_pdf_sha` set, and the `document.completed` `Audit.Log` at `flow.go:470` then hits a transient error (pool exhaustion, statement timeout acquiring the per-org advisory lock). The document is complete with no chain event binding `final_pdf_sha256`. A later party with object-store write swaps the accepted PDF and the evidence bundle has no completion event to cross-check against, so the swap is undetected. Signature-mode is bounded because the persisted ed25519 cert still provides independent tamper-evidence.
- Fix: emit the terminal completion, decline, and void events inside the same transaction as the terminal state write, OR add a reconciliation loop in `cmd/worker` that finds terminal documents lacking a chain-recorded terminal event and re-emits it idempotently. At minimum, stop discarding the `Audit.Log` error on the terminal transitions and route a failure into the stranded/retry path.
- Verification: CONFIRMED. Error-discard, fail-closed error return in `Log`, and the absence of any backfill are all directly visible; verifier held base at MEDIUM with a real conditional HIGH for acknowledgement-mode.

### MEDIUM

#### M1. Replayed or backfilled invoice.paid resurrects a cancelled subscription with a fabricated period
- file:line: `internal/billing/engine.go:229-243`, `periodOrDefault:267-274`; `internal/db/queries/billing.sql:20-31` (`UpsertOrgSubscription` `ON CONFLICT (org_id) DO UPDATE`, no WHERE), `:44-57` (`InsertBillingInvoice` `ON CONFLICT DO UPDATE`, not a hard unique violation).
- What is wrong: the `invoice.paid` branch hardcodes status `active` with no read of the current subscription status, no event-timestamp ordering check, and no guard that the period is not in the past. `periodOrDefault` fabricates `now..now+1mo` whenever the event omits the period (which Mollie often does). The idempotency the doc comment claims does not hold: `InsertBillingInvoice` is `ON CONFLICT DO UPDATE`, so even an exact-id replay does not error, the early-return never fires, and the code falls through to reactivate.
- Concrete scenario: a subscription is `cancelled` (the row is kept, `GetSubscriptionByProvider` has no status filter). The provider redelivers or backfills an old paid invoice. The handler flips the subscription back to `active` with a fresh forward-dated `now..now+1mo` window, re-granting paid entitlement to a cancelled account.
- Fix: add a status precondition to the reactivation path (do not move `cancelled`/`expired` to `active` on a stale invoice), add a monotonic event-timestamp or period-freshness guard, and reject an `invoice.paid` whose period is entirely in the past. Do not rely on `(provider, provider_payment_id)` uniqueness for idempotency, it is a DO UPDATE not a hard block.
- Verification: CONFIRMED. Gated behind provider replay behavior, not a direct external exploit (webhook signatures are validated), so MEDIUM.

#### M2. Compliance flags duplicated on every nightly tick, up to 14x, and resolved flags resurrect
- file:line: `internal/compliance/flagger.go:31-34` (comment claims dedup), `:107-126` (`flagForOrg`, unconditional insert); `internal/db/queries/compliance.sql:20-26` (`InsertComplianceFlag`, bare INSERT, no ON CONFLICT); `internal/db/migrations/00018_compliance.sql:27-49` (no unique index); `cmd/worker/compliance_rollup.go:45-47` (14-day lookback recomputed each tick).
- What is wrong: `FlagRun`'s comment asserts flags are inserted only when no open flag for the same (doc, update_ref) exists, but nothing implements it. There is no unique constraint, no `ON CONFLICT`, and no pre-select dedup. The only gate before insert is `bodyMentions`. The nightly `since := now - 14d` is recomputed each tick with no processed cursor, so a feed item stays in scope for about 14 nights.
- Concrete scenario: a feed item published on day 1 that matches org A's privacy notice produces one flag on night 1, another identical `open` flag on night 2, and so on for up to 14 nights. If the user resolves or acknowledges the flag, the next night re-inserts a fresh `open` one, making it impossible to clear for the lookback window.
- Fix: add a partial unique index on `(org_id, coalesce(document_id,...), coalesce(template_id,...), update_ref) WHERE status = 'open'` and change the insert to `ON CONFLICT DO NOTHING`, or pre-check for an existing open flag before inserting.
- Verification: CONFIRMED. Data-quality and UX defect, no data loss or cross-tenant leak, so MEDIUM.

#### M3. Public-mirror PII and internal-infra scrubbing is a literal denylist that gitleaks does not backstop
- file:line: `scripts/split-public-repo.sh:98-118` (16-entry `git filter-repo --replace-text` list), `.gitleaks.toml:7-23` (`useDefault = true` plus placeholder allowlist).
- What is wrong: gitleaks only classifies high-entropy secrets. Internal hostnames, IPs, and customer PII are not secrets, so their sole defense is the hand-maintained literal denylist. The list currently covers the prod IP, internal hosts, and exactly one real customer's PII (`anna@demobolaget.example`, `Demobolaget`, `Anna Exempel`). Any NEW internal host, staging IP, or real customer name or email committed into `hash/` later passes gitleaks and, being absent from the literal list, publishes to the public GitHub mirror unredacted. The presence of real customer PII in the denylist is evidence that live customer data reached this history once already.
- Concrete scenario: an engineer commits a test seed containing a real prospect's email into `hash/`, then runs `split-public-repo.sh --push`. gitleaks passes it (not a secret), the literal denylist does not contain it, and the email is published to the public fair-code mirror.
- Fix: add a positive-assertion pass before push that fails on broad patterns for the estate (internal `*.brightinteraction.com` subdomains not on an allow-list, RFC1918 plus the known prod /32, `@[a-z0-9-]+\.se` emails not in a synthetic-fixtures allow-list). Prefer synthetic fixtures over real customer data in tests and seeds.
- Verification: CONFIRMED. Structural defense-in-depth gap with a plausible PII leak path; currently-known PII is redacted, so MEDIUM not HIGH.

### LOW

#### L1. Doc-agent-token max_uses cap not atomically enforced, concurrency bypass
- file:line: `internal/auth/api_key_verifier.go:43,56` (read-then-check on a plain SELECT snapshot), `internal/auth/api_key.go:99,104-106` (async best-effort `Touch` on a detached `context.Background()` goroutine), `internal/db/queries/doc_agent_tokens.sql:23-27` (unconditional `used_count = used_count + 1`, no cap guard in WHERE).
- What is wrong: the `max_uses` check reads `used_count` from an unlocked lookup, while the increment is a separate, async, unconditional UPDATE that can never signal cap-exhausted. Check and increment are not atomic and are not even ordered (the increment can commit after several later requests read the stale count).
- Concrete scenario: a valid `max_uses=1` token with `used_count=0`. Fire 10 concurrent MCP requests. All 10 read `used_count = 0 < 1`, all pass the constant-time hash compare, all 10 are authorized. The single-use cap is bypassed. Abuse requires already holding the full valid token secret, which is why this is LOW.
- Fix: enforce the cap inside the UPDATE, `UPDATE ... SET used_count = used_count + 1 WHERE id = $1 AND (max_uses = 0 OR used_count < max_uses)`, run it synchronously in the auth path, and treat zero rows affected as "cap exhausted, reject".
- Verification: CONFIRMED. Separately, the 2026-07-17 TOCTOU fix that this finding examined is itself CONFIRMED CORRECT: `Touch` runs only after `subtle.ConstantTimeCompare` succeeds and touches both `TouchAPIKey` and `TouchDocAgentToken`.

#### L2. Placeholder secrets dual-allowlisted in both gates with no fixture back-reference
- file:line: `scripts/split-public-repo.sh:68` (coarse grep whitelist), `.gitleaks.toml:17-18` (gitleaks allowlist).
- What is wrong: `molliepathsecret16` and `mollie-test-key` are allow-listed in both gates, `dev-webhook-secret` in the coarse grep. These are standing exceptions with no comment tying them back to their fixture origin, so a future engineer who reuses one of these strings as a real credential would have it silently pass both secret gates and publish.
- Concrete scenario: someone sets `HASH_WEBHOOK_SECRET=dev-webhook-secret` in a real config, or promotes `mollie-test-key` to a live value; both gates suppress it on the next `--push`.
- Fix: confirm each maps to a committed test fixture, add a code comment at the fixture definition pointing back to the allowlist entry, and drop any entry not actually present in fixtures.
- Verification: CONFIRMED as a hygiene finding at LOW. All three tokens are provably synthetic today (two exist only inside a `t.Setenv` test helper at `internal/config/config_test.go:292-293`, `dev-webhook-secret` is a docker-compose dev fallback that production overrides), so there is no live exposure, only the standing-exception risk.

#### L3. i18n T placeholder substitution is order-dependent
- file:line: `internal/i18n/i18n.go:36-38` (map-range `strings.ReplaceAll` per key).
- What is wrong: `T` substitutes params by ranging a Go map (random order) and applying `strings.ReplaceAll` per key, so an already-substituted value that literally equals another live `{token}` gets re-expanded non-deterministically.
- Concrete scenario: a document named `"{org}"` rendered with `org = "EvilCorp"` produces either `"Doc: EvilCorp from EvilCorp"` or `"Doc: {org} from EvilCorp"` depending on iteration order (verifier reproduced 1780 vs 220 out of 2000 runs). The security framing is refuted: the real magic link is spliced outside `T` and HTML-escaped, so no URL can be rewritten. Impact is cosmetic garbling of an email string an attacker would target at their own recipients.
- Fix: substitute in a single pass (build the output from a regexp scan of `{token}` occurrences, resolving each token against the param map exactly once) instead of sequential `ReplaceAll`.
- Verification: CONFIRMED as order-dependent behavior, LOW, cosmetic only.

## Dropped (REFUTED, do not action)

- Quota warning "silently lost on a mail outage" (`cmd/worker/quota_warnings.go:100-111`): REFUTED. The worker's `mailer` is the queue-backed `QueueingMailer` (`cmd/worker/main.go:203`), whose `Send` enqueues into `email_deliveries` and returns nil regardless of SMTP health; a separate drain loop retries delivery with backoff. On a mail outage the warning is durably queued, so `MarkQuotaWarningSent` is set legitimately and nothing is lost. Only residual is a narrow crash-window duplicate email (LOW, no billing impact), not the claimed lost-warning-then-402.
- Coarse pre-flight secret gate "inert under pipefail plus SIGPIPE" (`scripts/split-public-repo.sh:66-73`): REFUTED. The intermediate greps block-buffer, so a realistic leak of a few matching lines is emitted in a single flush; `grep -q` reads it and exits 0 and the REFUSE branch fires correctly. The SIGPIPE-to-141 failure only manifests above roughly 64KB of post-filter matches (thousands of lines), which is not the shape of a real credential leak. The authoritative gitleaks scan independently gates `--push`.
